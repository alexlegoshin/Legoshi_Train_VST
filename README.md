# Amber

Консольный инструмент для акустического анализа сведённого трека против
персонального профиля вкуса ("пресета"). Считает громкость/динамику,
спектральный баланс, психоакустику, стерео, реверберацию и вокальный питч
по всему треку и по скользящему окну, отдельно на миксе и на выделенных
вокале/басе/барабанах/остальном инструментале — и сравнивает результат с
диапазонами значений, которые статистически связаны с оценкой "нравится"
на обучающей выборке.

Не делает автоматических правок звука и не использует нейросети для
принятия решений (Demucs — единственное ML-звено, и только для разделения
источников, не для оценки). Результат — таблица «метрика → диапазон
`нравится`/`не нравится`/непонятно», не готовое решение.

Методология и происхождение пресета — `documentation/`.

## Установка

```bash
python3 -m venv .venv && source .venv/bin/activate   # или используйте существующее окружение
pip install -r requirements.txt
```

Python 3.10+. `torch`/`demucs` нужны только для режима 1 (см. ниже) —
если разделение источников не требуется (у вас уже есть дорожки), можно
не ставить их и использовать только режим 2.

## Быстрый старт

Положить файл или папку в `import/`, запустить:

```bash
python orchestrate.py                 # обработать всё новое в import/
python orchestrate.py "трек.wav"       # обработать один конкретный элемент
python orchestrate.py --deep-psychoacoustics   # + настоящий sharpness/roughness (медленно)
```

Результат — в `output/<имя>_<таймстемп>/report.txt` (читаемая таблица) и
`measurements.json` (сырые числа, машиночитаемо).

## Два режима входа

### 1. Целый трек (файл в `import/`)

Единственный аудиофайл (`.wav`/`.mp3`/`.flac`/`.aiff`/`.aif`) без отдельных
дорожек. Запускается Demucs (`htdemucs_ft`, 4-стемовая модель) →
`vocals.wav` / `bass.wav` / `drums.wav` / `other.wav`. Дальше метрики
считаются на миксе и на каждом из четырёх ML-разделённых источников.

Ограничение: Demucs — приближение, не идеальное разделение (утечки между
стемами, артефакты на границах спектра). Используется НЧ-фильтр 10кГц
перед спектральными метриками на разделённых источниках — выше Demucs
шумит сильнее всего, полоса `air` (8-16кГц) на разделённых источниках не
считается вовсе.

### 2. Трек-аут (папка в `import/`)

Папка с несколькими файлами: один главный референс-микс + отдельные
дорожки записи. Работает на настоящих сигналах, не на ML-приближении —
точнее там, где есть исходный мультитрек.

**Определение ролей — по ключевым словам в имени файла, английским или
русским** (регистр не важен, устойчиво к NFC/NFD-разложению кириллицы на
macOS):

| роль | ключевые слова в имени |
|---|---|
| главный микс | `main`, `mix`, `master`, `full`, «микс», «мастер», «общ», «итог» (ровно один файл в папке) |
| вокал | `vocal`, `vox`, `voice`, `choir`, `bgv`, «вокал», «голос», «бэк», «хор» |
| бас | `bass`, «бас» |
| барабаны | `drum`, `kick`, `snare`, `hihat`, `hi-hat`, `hat`, `overhead`, `tom`, `cymbal`, `perc`, `percussion`, «драм», «удар», «бочк», «малый», «хай», «том», «тарелк», «перкусс» |
| остальное | всё, что не подошло под вокал/бас/барабаны (гитары, клавиши, синтезаторы и т.д.) |

Если роль не распознана ни по одному слову — трек уходит в «остальное» по
умолчанию, и оркестратор явно предупреждает об этом в `report.txt`, не
молчит.

Дорожек одной роли может быть несколько (например два вокальных дубля,
несколько микрофонов на барабанах) — они суммируются в один сигнал на
роль перед расчётом метрик. Если в имени нет ни одного из ключевых слов —
дорожка попадает в «остальное»; если не нашёлся ровно один файл-кандидат
на главный микс — прогон падает с понятной ошибкой (без микса не с чем
сравнивать роли).

Пример структуры папки:
```
import/my_mix/
  main.wav
  vocal_lead.wav
  vocal_double.wav
  bass.wav
  drums.wav
  guitar_rhythm.wav
  guitar_lead.wav
```

## Что считается

Для каждого источника (mix + до 4 ролей) — на двух уровнях:

- **Среднее по треку** — одно число на файл. Громкость/динамика (LUFS,
  LRA, PLR, crest factor, DR), спектральная форма (наклон, доли энергии
  по полосам, skewness), психоакустика (warmth ratio, harshness, плюс
  стационарные loudness/sharpness/tonality через MoSQITo), стерео-картина
  (только на миксе), реверберация (RT60/EDT/DRR/C50/C80 по изолированным
  хвостам после онсетов). На вокале дополнительно — F0-статистика,
  вибрато, интонация, признаки автотюна, форманты.
- **Скользящее окно** (4с, шаг 1с, энергетический гейт −45дБFS) — те же
  спектральные/психоакустические метрики по времени, плюс на вокале —
  voiced-доля и вибрато по окну. Опционально (`--deep-psychoacoustics`) —
  настоящий покадровый sharpness/roughness (MoSQITo), на вокале.
- **Секции** (только на миксе) — третий уровень гранулярности, между окном
  и целым треком: границы либо из ручной разметки (`_analysis/sections.csv`,
  если есть для конкретного трека), либо автосегментация по
  self-similarity+novelty. На каждую секцию — LUFS относительно среднего по
  треку; сводная метрика `arc_db` — драматургическая арка (контраст между
  началом и кульминацией трека). Таблица «секция → уровень» печатается в
  отчёте отдельным блоком.

Перед скользящим окном весь сигнал приводится к −18 LUFS integrated
(гейн считается по целому миксу и применяется одинаково ко всем его
источникам) — иначе пороги энергетического гейта и абсолютные значения
между разными по громкости мастерингами несравнимы.

Полный список метрик, формулы, библиотеки и обоснование, почему что-то
включено или сознательно не включено — `documentation/metrics.md`.

## Что НЕ входит в стандартный прогон

- Попарный анализ фазовой интерференции между дублирующими дорожками и
  психоакустическое маскирование одной дорожки другой — эти проверки
  осмысленны только на РЕАЛЬНЫХ одновременно записанных дублях (два живых
  вокальных дубля одной фразы и т.п.), а не на ML-разделении, где такого
  разделения на дубли физически нет. В коде это есть
  (`analysis/legacy_scripts/`), но не подключено к оркестратору — не
  универсально применимо к произвольному входу.
- Автоматическая правка звука. Инструмент только измеряет и сравнивает с
  диапазонами, решения — за пользователем.

## Оценка результата: пресет

Диапазоны «нравится»/«не нравится» на метрику — не встроены в код,
хранятся отдельно как данные: `presets/amber.json`. Формат пресета,
как он был получен и как сделать свой — `documentation/`.

Каждая запись пресета помечена уровнем надёжности (`high`/`medium`/`low`/
`pending`/`no_zone`), который реально взвешивает итоговый счёт в отчёте
(`high`=1.0 … `pending`/`no_zone`=0 — не влияют), а не просто
информативная метка.

```bash
python orchestrate.py --preset amber   # по умолчанию
```

## Структура проекта

```
Project/
  orchestrate.py          вход, CLI
  analysis/
    engine.py               сборка метрик по источнику (среднее + окно)
    verdict.py               сопоставление измерений с пресетом
    alignment.py              GCC-PHAT выравнивание дорожек (режим 2)
    sections.py                секционная гранулярность: ручная разметка/
                                автосегментация, драматургическая арка
    metrics/                 чистые вычислительные модули (без побочных
                              эффектов, без зависимости от конкретного трека)
    legacy_scripts/          исследовательский код, которым был получен
                              пресет (батч-раннеры, корреляционный анализ,
                              опросник для сбора обучающих оценок) — не
                              часть рабочего пайплайна, оставлен для
                              воспроизводимости и дальнейших расширений
  presets/
    amber.json                данные: диапазоны метрик
  tests/
    synthetic/                 юнит-тесты на синтетических сигналах
                                с известным ответом — быстрые
    invariance/                 тесты на реальном корпусе (инварианты,
                                 покрытие ключей пресета) — медленные,
                                 не входят в штатный быстрый прогон
  documentation/               методология, откуда взялись диапазоны,
                               обоснование по каждой метрике, происхождение
                               каждой зоны пресета (`preset-provenance.md`)
  import/, output/             рабочие папки (вход/выход прогонов)
```

## Формат отчёта

`report.txt`: версия пресета (имя + sha256, чтобы отличать правки одного
имени файла друг от друга), для режима 1 — версия/параметры Demucs;
взвешенный итог (−100%…+100%, знак и величина = насколько измеренные
метрики совпадают с зоной «нравится» с учётом веса надёжности; если
измерено меньше половины применимых зон — вместо процента честное «данных
недостаточно», не вводящее в заблуждение число); предупреждение, если
зона, откалиброванная на Demucs-стемах, применена к реальному трек-ауту
(или наоборот); исходные параметры входных файлов; таблица «секция →
уровень» (если применимо); факты о входе, которые не метрики (срез
кодека, дуал-моно, клиппинг); отдельный блок «что НЕ измерено и почему»
(структурные пропуски вроде air-полосы на разделённых стемах, реверба на
ML-источниках); и в конце — таблица метрика × источник × статус ×
(надёжность, тип свидетельства).

`measurements.json` — та же информация машиночитаемо:
- `measurements` — плоский словарь `"источник::метрика": значение` (для
  оконных метрик — медиана и число окон, прошедших энергетический гейт);
- `diagnostics` — факты о каждом источнике (срез кодека, дуал-моно,
  клиппинг, причина пропуска реверба и т.п.);
- `run` — версия пресета (хэш), параметры Demucs, режим входа;
- `trackout` — только для входов с реальными дорожками: исходные форматы
  файлов, исключённые из-за рассинхрона дорожки;
- `section_profile` — только если посчитана драматургическая арка:
  источник границ секций (`manual`/`auto`) и таблица секций.
