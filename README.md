# Legoshi Train

Консольный инструмент для акустического анализа сведённого трека против
персонального профиля вкуса ("пресета") — ядро будущего VST3-плагина
(дорожная карта и статус — `documentation/roadmap.md`). Считает
громкость/динамику, спектральный баланс, психоакустику, стерео,
реверберацию и вокальный питч по всему треку и по скользящему окну,
отдельно на миксе и на выделенных вокале/басе/барабанах/остальном
инструментале — и сравнивает результат с диапазонами значений, которые
статистически связаны с оценкой "нравится" на обучающей выборке.

Поверх сравнения с пресетом — два слоя диагностики:

- **Восстановление** («без выбора» — клиппинг, гул): точное место,
  параметры и родовая категория фикса, без гадания.
- **Вкусовые правки** («с выбором» — EQ/динамика/сатурация): полный
  список рекомендаций за один запуск, сгруппированный по стадиям
  сведения, с конкретным ходом и его округлёнными параметрами. Выбор
  хода не по домыслу, а по реально измеренному эффекту (свой DSP-симулятор
  канонических ходов + матрица «ход → сдвиг метрики», откалиброванная
  против реальных версий сведения).

Плюс отдельные измерения: наложение дублей (расхождение по времени/питчу,
риск гребёнки — решение художественное, инструмент не выбирает за вас),
психоакустическое маскирование между дорожками (кто кого перекрывает).

**Инструмент не делает автоматических правок звука** — ни для одной
категории, включая однозначные вроде гула, для которого в коде есть
рабочий, протестированный notch-фильтр, но продукт им никогда не
пользуется сам. Он только говорит: «здесь, вот это, вот этим». Применяет
пользователь, в своей DAW. Нейросети не используются для принятия
решений (Demucs — единственное ML-звено, и только для разделения
источников). Результат — таблица «метрика → диапазон `нравится`/`не
нравится`/непонятно» плюс список рекомендаций, не готовое решение и не
применённая правка.

Методология и происхождение пресета — `documentation/`.

## Установка

```bash
python3 -m venv .venv && source .venv/bin/activate   # или используйте существующее окружение
pip install -r requirements.txt
```

Python 3.10+. `torch`/`demucs` нужны только для режима 1 (см. ниже) —
если разделение источников не требуется (у вас уже есть дорожки), можно
не ставить их и использовать только режим 2.

## Быстрый старт

Положить файл или папку в `import/`, запустить:

```bash
python orchestrate.py                 # обработать всё новое в import/
python orchestrate.py "трек.wav"       # обработать один конкретный элемент
python orchestrate.py --deep-psychoacoustics   # + настоящий sharpness/roughness (медленно)
```

Результат — в `output/<имя>_<таймстемп>/report.txt` (читаемая таблица) и
`measurements.json` (сырые числа, машиночитаемо).

## Два режима входа

### 1. Целый трек (файл в `import/`)

Единственный аудиофайл (`.wav`/`.mp3`/`.flac`/`.aiff`/`.aif`) без отдельных
дорожек. Запускается Demucs (`htdemucs_ft`, 4-стемовая модель) →
`vocals.wav` / `bass.wav` / `drums.wav` / `other.wav`. Дальше метрики
считаются на миксе и на каждом из четырёх ML-разделённых источников.

Ограничение: Demucs — приближение, не идеальное разделение (утечки между
стемами, артефакты на границах спектра). Используется НЧ-фильтр 10кГц
перед спектральными метриками на разделённых источниках — выше Demucs
шумит сильнее всего, полоса `air` (8-16кГц) на разделённых источниках не
считается вовсе. Наложение дублей (расхождение дублирующих вокальных
дорожек) в этом режиме не измеряется — у Demucs-разделения нет понятия
"дубль", только один стем на роль.

### 2. Трек-аут (папка в `import/`)

Папка с несколькими файлами: один главный референс-микс + отдельные
дорожки записи. Работает на настоящих сигналах, не на ML-приближении —
точнее там, где есть исходный мультитрек. Если дорожек одной роли
несколько (например два вокальных дубля) — до их суммирования в общий
сигнал роли считается попарное измерение наложения (расхождение по
времени/питчу, верхняя оценка риска гребёнки), само наложение — тоже
только измерение, финальное решение (свести/развести/оставить) — за
пользователем.

**Определение ролей — по ключевым словам в имени файла, английским или
русским** (регистр не важен, устойчиво к NFC/NFD-разложению кириллицы на
macOS):

| роль | ключевые слова в имени |
|---|---|
| главный микс | `main`, `mix`, `master`, `full`, «микс», «мастер», «общ», «итог» (ровно один файл в папке) |
| вокал | `vocal`, `vox`, `voice`, `choir`, `bgv`, «вокал», «голос», «бэк», «хор» |
| бас | `bass`, «бас» |
| барабаны | `drum`, `kick`, `snare`, `hihat`, `hi-hat`, `hat`, `overhead`, `tom`, `cymbal`, `perc`, `percussion`, «драм», «удар», «бочк», «малый», «хай», «том», «тарелк», «перкусс» |
| остальное | всё, что не подошло под вокал/бас/барабаны (гитары, клавиши, синтезаторы и т.д.) |

Если роль не распознана ни по одному слову — трек уходит в «остальное» по
умолчанию, и оркестратор явно предупреждает об этом в `report.txt`, не
молчит.

Если в имени нет ни одного из ключевых слов — дорожка попадает в
«остальное»; если не нашёлся ровно один файл-кандидат на главный микс —
прогон падает с понятной ошибкой (без микса не с чем сравнивать роли).

Пример структуры папки:
```
import/my_mix/
  main.wav
  vocal_lead.wav
  vocal_double.wav
  bass.wav
  drums.wav
  guitar_rhythm.wav
  guitar_lead.wav
```

## Что считается

Для каждого источника (mix + до 4 ролей) — на трёх уровнях:

- **Среднее по треку** — одно число на файл. Громкость/динамика (LUFS,
  LRA, PLR, crest factor, DR), спектральная форма (наклон, доли энергии
  по полосам, skewness), психоакустика (warmth ratio, harshness, плюс
  стационарные loudness/sharpness/tonality через MoSQITo), стерео-картина
  (только на миксе), реверберация (RT60/EDT/DRR/C50/C80 по изолированным
  хвостам после онсетов, плюс группировка по позиции на треке — см. ниже).
  На вокале дополнительно — F0-статистика, вибрато, интонация, признаки
  автотюна, форманты.
- **Скользящее окно** (4с, шаг 1с, энергетический гейт −45дБFS) — те же
  спектральные/психоакустические метрики по времени, плюс на вокале —
  voiced-доля и вибрато по окну. Опционально (`--deep-psychoacoustics`) —
  настоящий покадровый sharpness/roughness (MoSQITo), на вокале.
- **Секции** (только на миксе) — третий уровень гранулярности, между окном
  и целым треком: границы либо из ручной разметки (`_analysis/sections.csv`,
  если есть для конкретного трека), либо автосегментация по
  self-similarity+novelty. На каждую секцию — LUFS относительно среднего по
  треку; сводная метрика `arc_db` — драматургическая арка (контраст между
  началом и кульминацией трека). Таблица «секция → уровень» печатается в
  отчёте отдельным блоком. Та же сетка секций используется для атрибуции
  вкусовых замечаний (см. ниже) — «хуже всего в припеве», не таймкод.

Перед скользящим окном весь сигнал приводится к −18 LUFS integrated
(гейн считается по целому миксу и применяется одинаково ко всем его
источникам) — иначе пороги энергетического гейта и абсолютные значения
между разными по громкости мастерингами несравнимы.

Плюс два «среднемасштабных» диагностических окна (~15с, отдельно от
трёх уровней метрик выше): гул проверяется не только по всему треку
целиком, но и по интервалам — так видно, присутствует ли наводка
действительно всюду (сетевая) или только в части записи (артефакт
монтажа); реверб-диагностика группируется так же, для отделения бликида/
случайной вставки от общей акустики трека.

Полный список метрик, формулы, библиотеки и обоснование, почему что-то
включено или сознательно не включено — `documentation/metrics.md`.

## Диагностика и рекомендации

### Восстановление («без выбора»)

Клиппинг (локализация, длительность, канал, классификация click/sustained)
и гул (детекция + уточнение частоты до долей Гц параболической
интерполяцией) — точный ответ, не вопрос вкуса. Рекомендация — родовая
категория и параметры («на 0:23 нужен dehum на 50.3Гц»), не встроенная
репарация: готовая, протестированная функция устранения гула есть в коде
(`analysis/metrics/noise.remove_narrowband_hum`), но продукт её не
вызывает — ни автоматически, ни как часть потока.

### Вкусовые правки («с выбором»)

Для каждой метрики, вышедшей за зону пресета — рекомендация: конкретный
ход (сейчас родовое имя из встроенного DSP-симулятора, позже — конкретный
плагин из каталога), стадия сведения (для группировки вывода), секция
трека (не таймкод — скользящее окно не даёт чёткой границы события),
округлённые параметры («колокол, срез ~3дБ на ~300Гц»), уверенность.

Выбор хода — не по домыслу. В `analysis/interventions.py` — 10
канонических DSP-ходов (колокол/полка EQ, мягкий компрессор, мягкая
сатурация). Они прогнаны по корпусу реальных треков
(`analysis/build_interference_matrix.py`), измерен реальный сдвиг каждой
метрики от каждого хода — таблица `presets/interference_matrix.json`.
Рекомендация для конкретной метрики берёт ход из этой таблицы, а не из
одной лишь DSP-интуиции — кандидат без эмпирического подтверждения
правильного направления не рекомендуется, даже если по смыслу должен был
бы подойти. Таблица откалибрована против реальных версий одного трека у
профессионального инженера сведения
(`analysis/calibrate_interference_matrix.py`,
`presets/calibration_report.json`) — насколько предсказания симулятора
совпадают по знаку с тем, что реально произошло между версиями.

Полный список выдаётся за один запуск анализа, не по одной правке —
сколько раз перезапускать анализ после ручных правок, решает
пользователь. Одна и та же роль с противоположными ходами на одном
физическом параметре (напр. рекомендован и срез, и подъём одной и той же
полосы) — честно помечается как конфликт, не молчим и не выбираем сами.

Наложение дублей — тут же, но не автоматический вывод: измерение плюс
явное «реши сам» (свести в ноль, развести эффектом хоруса, развести
только по панораме).

**Панорама/стерео-позиционирование сознательно вне анализа** — финальный
творческий штрих, который пользователь берёт на себя сам, по слуху.

## Психоакустическое маскирование

Между всеми парами отдельных источников (не с миксом — сумма всего не
может маскировать сама себя) — доля времени/частоты, где источник
физически слышен поверх остальных (ERB-полосы, психоакустическая
spreading function, прямое и обратное маскирование по времени), и
попарная атрибуция «кто кого перекрывает» (только пары заметнее 5%).
Тоже только измерение — рекомендация по фиксу пока не формализована.

## Оценка результата: пресет

Диапазоны «нравится»/«не нравится» на метрику — не встроены в код,
хранятся отдельно как данные: `presets/legoshi_amber.json` — оригинальный
пресет разработчика («тёплый/аналоговый» профиль вкуса), возможны и
другие профили параллельно (жанр/пользователь/настроение), формат один и
тот же. Формат пресета, как он был получен и как сделать свой —
`documentation/`.

Каждая запись пресета помечена уровнем надёжности (`high`/`medium`/`low`/
`pending`/`no_zone`), который реально взвешивает итоговый счёт в отчёте
(`high`=1.0 … `pending`/`no_zone`=0 — не влияют), а не просто
информативная метка.

```bash
python orchestrate.py --preset legoshi_amber   # по умолчанию
```

## Структура проекта

```
Project/
  orchestrate.py          вход, CLI
  analysis/
    engine.py               сборка метрик по источнику (среднее + окно)
    verdict.py               сопоставление измерений с пресетом, дельта до зоны
    alignment.py              GCC-PHAT выравнивание дорожек (режим 2)
    sections.py                секционная гранулярность: ручная разметка/
                                автосегментация, драматургическая арка
    section_attribution.py      атрибуция вкусовых замечаний по секциям
    recommendations.py           Recommendation — единая точка: восстановление
                                  и вкусовые правки, оба слоя рекомендаций
    interventions.py              10 канонических DSP-ходов симулятора
    build_interference_matrix.py   прогон ходов по корпусу -> таблица дельт
    calibrate_interference_matrix.py  калибровка таблицы против реальных
                                       версий сведения
    metrics/                 чистые вычислительные модули (без побочных
                              эффектов, без зависимости от конкретного трека):
                              включая layering.py (наложение дублей) и
                              masking_erb.py (психоакустическое маскирование)
    legacy_scripts/          исследовательский код, которым был получен
                              пресет (батч-раннеры, корреляционный анализ,
                              опросник для сбора обучающих оценок) — не
                              часть рабочего пайплайна, оставлен для
                              воспроизводимости и дальнейших расширений
  presets/
    legoshi_amber.json         данные: диапазоны метрик, оригинальный пресет
    interference_matrix.json    измеренные дельты «ход -> метрика»
    calibration_report.json      результат калибровки против реальных версий
  tests/
    synthetic/                 юнит-тесты на синтетических сигналах
                                с известным ответом — быстрые
    invariance/                 тесты на реальном корпусе (инварианты,
                                 покрытие ключей пресета) — медленные,
                                 не входят в штатный быстрый прогон
  documentation/               методология, откуда взялись диапазоны,
                               обоснование по каждой метрике, происхождение
                               каждой зоны пресета (`preset-provenance.md`),
                               дорожная карта к VST3-плагину (`roadmap.md`)
  import/, output/             рабочие папки (вход/выход прогонов)
```

## Формат отчёта

`report.txt`: версия пресета (имя + sha256, чтобы отличать правки одного
имени файла друг от друга), для режима 1 — версия/параметры Demucs;
взвешенный итог (−100%…+100%, знак и величина = насколько измеренные
метрики совпадают с зоной «нравится» с учётом веса надёжности; если
измерено меньше половины применимых зон — вместо процента честное «данных
недостаточно», не вводящее в заблуждение число); предупреждение, если
зона, откалиброванная на Demucs-стемах, применена к реальному трек-ауту
(или наоборот); исходные параметры входных файлов; таблица «секция →
уровень» (если применимо); факты о входе, которые не метрики (срез
кодека, дуал-моно, клиппинг, наложение дублей, маскирование между
дорожками); рекомендации по очистке (клиппинг/гул); атрибуция вкусовых
замечаний по секциям; рекомендации по вкусовым правкам, сгруппированные
по стадиям сведения; отдельный блок «что НЕ измерено и почему»
(структурные пропуски вроде air-полосы на разделённых стемах, реверба на
ML-источниках); и в конце — таблица метрика × источник × статус ×
(надёжность, тип свидетельства).

`measurements.json` — та же информация машиночитаемо:
- `measurements` — плоский словарь `"источник::метрика": значение` (для
  оконных метрик — медиана и число окон, прошедших энергетический гейт);
- `diagnostics` — факты о каждом источнике (срез кодека, дуал-моно,
  клиппинг, причина пропуска реверба, наложение дублей, маскирование и т.п.);
- `run` — версия пресета (хэш), параметры Demucs, режим входа;
- `trackout` — только для входов с реальными дорожками: исходные форматы
  файлов, исключённые из-за рассинхрона дорожки;
- `section_profile` — только если посчитана драматургическая арка:
  источник границ секций (`manual`/`auto`) и таблица секций;
- `restoration_recommendations` — рекомендации по очистке (Блок 2);
- `taste_recommendations` — рекомендации по вкусовым правкам (Блок 7).

## Куда движется проект

Консольный инструмент — рабочее ядро будущего VST3-плагина: тот же
рекомендательный принцип (программа никогда не применяет фикс сама),
упакованный в плагин с захватом аудио прямо из DAW. Полный план,
статус по блокам и архитектурные решения — `documentation/roadmap.md`.
